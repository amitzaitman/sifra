# sifra: architecture for milestone 1

For agents. The engineering contract for milestone 1 (`decisions.md`, "שלב 2: אבן הדרך הראשונה"): the shell, three
games (`ten-frame` and `balance`, the milestone's first plan, then `stories`), tests and CI. The shell is built first,
on branch `app/shell`; the first two games are then built in parallel against sections 2 and 7. Where this file and a pedagogy or design doc disagree, the doc wins: stop
and report. Section 6 lists the gaps in the docs that this file closes. Sizes measured on today's code (pixels,
bytes, line counts) are not copied here, as they go stale: where a test measures one, the text names the test. A
figure that says why a choice was made, as it was measured then, stays. Read with it: [rules.md](rules.md),
[dev-spec.md](dev-spec.md) (A.1 round data, A.2 checks), [design.md](design.md), [pedagogy.md](pedagogy.md) §5 and
§6, [skills.md](skills.md), [depth/README.md](depth/README.md) (§4.1), [depth/errors.md](depth/errors.md) (§4.2).
Game 3, `stories` (pedagogy §6.4, design §6.10), is built against the same contract, docs first (decisions.md,
2026-10-30): what it adds to the shell, lib/ and the tests is marked "game 3" below, and its rows are in section 6.
It is built (2026-10-30): its game folder, its registry line and rounds lock, tests/stories.test.js and
e2e/stories.spec.js (4.9). Like the other two, it goes live only after the owner's iPhone check (section 6, "When a
game goes live"), and the three go live together (2026-11-01, section 6).

## 2. The game module contract

### 2.1 Exports

```js
// games/<id>/game.js. No side effects at import: no DOM, no storage, no timers.
export const meta = {
  id: 'ten-frame',                        // the folder name
  title: 'מִסְגֶּרֶת עֶשֶׂר',                  // with nikud: game card, hidden <h1>, <title>
  version: 1,                             // bump when makeRound output changes for the same level and seed (lock, 4.1)
  css: new URL('game.css', import.meta.url).href,   // the shell links it at start (home thumbs draw every game)
};
export const levels = [];                 // Level objects (2.2). Level n is levels[n - 1]
export const text = [];                   // locked sentence templates (R1). round.text is '' or one of them
export const rules = {};                  // ruleId: (round) => value, for every rule the game's choices use
export const displays = [];               // the display ids it draws; miss throws on any other (below)
export function makeRound(level, rng) {}  // pure; returns a Round (2.3)
export function render(host, round, ctx) {}   // draws the picture into host; returns a RoundView (2.4)
export function face(host, value, round) {}   // optional: draws a card face; returns false for the plain number
export function classify(round, value) {}     // build and estimate rounds only (A.1); none in milestone 1
export function budget(round, choice) {}      // optional: why a wrong choice's display does not fit, else null (4.2)
export function canShow(round, choice) {}     // optional: can this round's picture draw a choice's display
```

`displays` lists, each once, the ids of the §4.2 catalogue's displays that the game draws. Its `miss` (2.4) draws a
display through a table keyed by these ids, and throws an Error on any other id (the balance: on any display its
round has no drawing for) before it changes the picture, so a display never falls through to another one's drawing.
`canShow(round, { value, rule })` says whether this round's picture can draw that choice's display
(`RULES[rule].display`): a game whose drawing depends on more than the id exports it, and its `makeRound` deals no
wrong choice that `canShow` rejects; the next rule in the skill's list takes the place, as with a budget (4.2). The
ten-frame: each kind of picture (frame, bond, pair cards, bundles, bundles with a cover, two frames) has its own table
in help.js, a count-up from the bundle needs 10 or more, and a frame's empty plate needs an empty unknown; its
drawings throw on the same cases. The balance: view.js keeps a table per scene (the pans draw each display their own
way, a judging card and the turned rows draw each as ghosts), and `drawable` there gives the jumps to `? = a + b`
and to a missing part (from the known part's last cube, 2026-10-31); its `budget` says no where `canShow` does, and
where the rows do not fit. So a rule of the skill's list whose
display the picture cannot draw is skipped without a word: the level names each such rule in `undrawn` (2.2), and the
generic test fails a game that deals such a card anyway, and a level that does not name such a rule (4.2).

Game 3, `stories`, exports `meta`, `levels`, `text` (`[]`), `rules`, `displays` (`overflow`, `flash`, `count-up`,
`jumps`), `budget`, `canShow`, `makeRound` and `render`; no `face`, no `classify`. Its `canShow` says no to a 0: every
display fills, counts or flashes places, so a 0 has nothing to draw (op.other where the two numbers are equal, `2 + 2`;
playtest 2026-10-31), and levels 1, 2 and 8 list `op.other` in `undrawn`. Its `budget` says no to a display that needs more than 4 rows (2 of the story, 2 for the
display; design 6.10), from the round alone, never from a viewport or a pixel constant, so changing a stroke never
changes makeRound's output.

No grade anywhere: not in `meta`, not in a level, not in the shell. Levels and progression are independent of
school grade (owner decision 2026-10-14, pedagogy §8.1); the generic test fails a `meta` with a grade key (4.2).

### 2.2 Levels

- One complete plain object per level (build the list with spread; nothing is inherited at run time). Required: `id`
  (unique in the game, never reused: storage keys on it, so a level can be inserted later), `skill`, `demo`,
  `options` (3 or 4), `model`, `look`, `terms`; then the skills.md parameters the level needs, `min` when the
  range does not start at 0, and `forms`, `exclude`, `undrawn` and `samePlace` below. Nothing else outside the skills.md
  parameter table.
- `structure` or `ask` as an array makes a mixed level: the planner picks one per round and passes it in (R3, R11).
- `forms`: the forms makeRound deals, each `{ unknown, eqform, w }`: what it sets of the two (the rest is the
  level's, `eqform` `'standard'`) and its weight; a form's share is `w` over the sum. A level whose `unknown` is an
  array lists its forms (R2: every listed unknown is in one), and `eqform` is one value: a level that mixes forms
  lists them here (R8: the forms give 25% or more not standard). makeRound picks the form once per round with
  `pickWeighted(forms, rng)` (lib/weights.js, one draw), before any retry of the numbers, and retries only the
  numbers, so a rejected try never shifts the shares (the balance picks it first; the ten-frame, which never
  retries, after its numbers). The generic test measures each share against `w` (4.2). A split inside a form stays
  in the game's code, and the deal test does not measure it: ten-frame level 7's `10 − k = ?` in half its standard
  rounds (`minus`, a draw of its own) and level 9's `14 − 10 = ?` in half its standard rounds (`at`, where the
  form's draw fell inside its share; owner decision 2026-10-15); tests/ten-frame.test.js checks that each appears.
- `exclude`: the whole numbers of the level's range `[min ?? 0, max]` that are never an answer, each for a reason in
  a comment beside it (a known part is 1 or more, so a missing part is under the whole). The generic test fails
  a number of the range that is neither dealt nor listed, and a listed one that is dealt (4.2).
- `undrawn`: the rules of the skill's list that the game has, and whose display this level's picture cannot draw
  (`displays`, `canShow`, 2.1) on some of its rounds, each for a reason in a comment beside it. makeRound skips such
  a rule there in silence, so a skills.md edit that brings one in would change what a child meets without a word.
  The generic test fails a rule with such a round that is not listed, and a listed one that every round draws (4.2).
  Today only the stories list one: levels 1, 2 and 8 list `op.other`, 0 where the two numbers are equal, with nothing
  to draw (games/stories/game.js). The balance's `eq.sign.missing` levels listed `count.start-included` until the pans
  drew its jumps on a missing part, and the ten-frame's bridge levels until the two frames drew them (both 2026-10-31,
  section 6).
- `samePlace`: the reason, in words, why one card (or another simple rule, 4.2) finds the answer in 80% of the level's rounds, or of one of its forms' rounds, or more (R4, 4.2). The
  cards go small to large, so a level whose rule values all fall on one side of the answer would leave it on one card;
  makeRound varies its place (lib/place.js), and a level that cannot says why here. No level has one today. The
  generic test fails a level at 80% without it, and one with it below 80%.
- Levels are numbered from 1 wherever a person or a URL sees them (§6 tables, `#/dev`, records).

### 2.3 Rounds and rules

dev-spec A.1 is the shape, with these precisions:

- The round copies `skill`, `look` and `model`, and the picked `structure`, `unknown` and `eqform`.
- `equation`: `{ left, right }`, each a token list read left to right: numbers, `'?'`, and `'+'`, `'−'` (U+2212),
  `'×'`, `':'`, e.g. `{ left: [7, '+', '?'], right: [10] }`. With k `'?'` leaves the answer is an array of k numbers
  (pair cards). `null` before the level has symbols.
- Values by catalogue type: number: a number (an array of numbers on pair cards); relation: `'<'`, `'>'`, `'='`,
  `'left'`, `'right'` or `'level'`; card: an equation object; picture: a plain object that `face` draws; order: an
  array.
- `choices`: `[{ value, rule }]`, `rule: null` on the correct one only. Numbers ascending; other values in the order
  makeRound gives (shuffled with `rng`). The shell draws them in array order.
- Plain data only (survives `structuredClone`). In both milestone games `text` is `''` and `terms` is `[]`.
- `rules[id](round)` returns the predicted value. When the catalogue formula says "or" (`slip.near`, `slip.far`) it
  returns `{ oneOf: [a, b] }`, and a choice with that rule equals one of them.
- **Judging round** (`eq.sign.true-false`, the balance's `true-false` level): the answer is a card, an equation object
  with numbers and operators on both sides and no `'?'`; every choice is such a card; the answer card is true and every
  other card false. `equation` is `null` (the exercises are on the cards, so the equation row is empty until the round
  is solved; then the game writes the true card there with `setEquation`, so the full exercise is on screen, R5), there is no `unknown`
  and no §4.6 row, and `picture` is the game's own stage (it may hold no groups). The balance's judging round also
  carries `fact: [a, b]`, the exercise `a + b = c` every card is made of: a true `7 = 7` shows no parts, and the
  catalogue's card formulas need them (depth §4.9). Values compare by deep equality, whatever their key order. The shell's card label reads the tokens (`5 + 2 = 7`); `face` draws the card on one
  line and may set its own `aria-label`.

A picture that tells a story before its `?` (game 3, design 6.10) runs its event from the mount, under `[data-event]`,
and builds the equation row in step with it (`build`). There is no lock for it: the cards are live from the mount
(design 7.1 locks them only while a display runs). `miss` and `solve` first finish the event (every
animation under `[data-event]` finished, every token built, `[data-event]` removed), then run as usual, so a tap during
the event is an attempt like any other; `demo` waits for the event to end, as the child would. With reduced motion,
on abort and in thumbs the event is at its end state at once (in thumbs before `render` returns). `firstMs` keeps its
meaning (from the mount).

### 2.5 One round

1. The shell builds the level (adding the planner's `structure` or `ask`), calls `makeRound(level, rng(seed))`,
   freezes the round all the way down (`dealt` in app.js; a write to it throws, so neither the shell nor `render`
   can change what the record and the next steps read), finds the answer card, and runs the demo first when one is
   due (2.6). Thumbs, demos and `#/dev` get their rounds the same way.
2. It builds the screen (3.2): the panel host `[data-area="picture"][data-game]`, the equation row (each `'?'` a cover
   over an `.eq-answer` with `aria-hidden`, so a screen reader hears the `?` and not the answer), the cards (`face`,
   else the number, plus dots in rows of five when `look` is not `symbols`, the level's `cardDots` is not `false` and every
   value is an integer 0-20), then
   `view = render(host, round, ctx)`. In `symbols` look the panel holds the 96×96 picture button, which calls
   `view.picture()` and logs `picture`; after the solve it stays, still calls `view.picture()`, and logs nothing.
   Then `picture()` draws the solved picture, without the cover (2.4), as the equation shows the answer.
3. A correct tap (`deepEqual(value, answer)`, key order ignored) goes to step 5. A wrong tap: the shell retires the
   card (design §6.5), counts the miss, sets `step` to `min(3, misses)` with 4 options or `min(3, misses + 1)` with 3,
   locks the cards, calls `view.picture()` first in `symbols` look if the picture is not shown, awaits
   `view.miss({ value, rule, display, step, first })` (`display` from RULES, `first` true on the round's first miss),
   and unlocks. After step 3 only the answer card is left, ringed (design §6.5).
4. In `miss` the game removes the previous display and runs the new one (root `[data-display="<id>"]`; an id not in
   `displays` throws, 2.1); from step 2 it adds the hint (`[data-hint]`, kept to the end of the round, design §7.2;
   a 3-option level's first miss is
   step 2 and still a first miss: its display stays to the next tap, also with reduced motion, and the hint joins
   it); at step 3 the tour: one `[data-tour]`
   per digit, the last one the answer (from 1 on the unknown when it is a part, on from the known part when it is
   the whole; R5). It resolves when the display has ended and, at step 3, the tour; it does not wait for the
   hint's pulse, which goes on after the cards unlock (design §7.1-§7.2: the cards lock only while a display runs,
   the hint does not lock). At once with reduced motion, and on abort.
5. Correct: the shell takes the attempt (3.9) and, once the closing below has run (also when the round is left),
   reads storage again, applies the ladder (3.4), any stuck return (3.7) and the attempt, and writes them, so a long
   log's write never holds up the card's change (bug hunt #20) and another tab's write during the closing stays
   (bug hunt #8); then it marks the
   card, sets `data-solved` on the screen (app.css then shows `[data-role="unknown"]`, `.eq-answer` and any
   `.is-unbuilt` token), shows every token of the equation row itself (`buildEquation(row, null)` in
   shell/equation.js, so the row is no longer `aria-busy`; the game's `build` does nothing from here on; a tap during
   a story's event, 2.4, comes here before the game finishes the event), lifts the
   equation cover (it leaves the accessibility tree, and each answer comes back as a new node; the row is one atomic
   polite live region per round, refilled in place by setEquation, so a reader says the whole solved equation, design
   §6.4), awaits `view.solve()`, writes the attempt, reads the view's label again, then puts "הַבָּא" in the cards'
   place and focuses it (design §6.9). On "הַבָּא" it aborts
   `signal`, empties the host and starts the next round.

### 2.6 Demo and "show me how" (R9)

- The demo screen, `main[data-screen="demo"]`, has an overlay `[data-demo]` with the hand `[data-hand]`; its round
  comes from a derived seed (3.8), a plain round with other numbers than the round it shows how to solve; the cards
  stay locked; in `symbols` look the shell calls `view.picture()` at once, so the hand works on the help picture;
  the bar keeps the session's rounds done. `await view.demo?.(hand)`, then the hand taps the answer card and step 5
  runs; "הַבָּא" leads to the real round. No attempt is written; the next one lists the demo in `demo`. An entry
  demo counts as seen once the hand has tapped the answer (3.4).
- The hand (`Hand` in types.d.ts): `tap(el)` first scrolls the page, never the picture's panel, so that `el` and the
  hand under its middle are on screen (on a phone held sideways the round is taller than the screen), then moves the
  hand's tip onto the middle of `el` and taps. `rest()` hides it (it fades out), then puts it back at its place at the foot
  of the round, off the picture; the hand starts hidden and shows only on its way to what it taps (2026-11-01: on a
  short phone, 320×568 or 375×548, that place lies on the cards, and the resting hand covered one, usually a wrong
  one, through the hint and the tour; a judging round's hand never moved before its tap). A game's
  demo rests the hand before its hint and its tour, so it covers nothing they draw: the ten-frame in one place for
  every kind (game.js), the balance and the stories in their scenes. The hand aims again on every resize (a turned
  phone moves everything): at what it points at, and after the solve, when the answer card is gone, at "הַבָּא" in its
  place. A tap waits until the hand has arrived, also when a turn aimed it again on its way (the new aim cancels the
  move, and `settle` resolves on a cancel). After the solve the page scrolls so that "הַבָּא" is all on screen.
- What a demo shows is the game's: the ten-frame's and the stories' hands touch the picture's parts in order, then
  the hint and the tour (step 2 and 3, as a third miss draws them); the balance's touches the pans left to right (R7;
  an empty pan at its bowl, the turned rows at their cover), rests, then the hint and the tour; a judging round's pans
  are empty, so it starts at the hint. Level 10 of the ten-frame moves the counters instead (pedagogy 6.2).
- It runs on entry to a level with `demo: true` as 3.4 says (never in a review round), and once at any level after a
  stuck return (3.7).
- The hand button (always in the bar) aborts the round, runs a demo at its level, then mounts the same round again
  from the start. The record goes on, with `how` added, so the outcome is at best `help`.
- With reduced motion the demo jumps to its end states; the child sees it solved and taps "הַבָּא".

### 2.7 Cleanup and motion (R10)

- Every listener is added with `{ signal }`. After abort, never touch `host`. No module state between rounds.
- No `setTimeout`, `setInterval` or `requestAnimationFrame` in any site code (games/, lib/, shell/, app.js). Sequences
  chain on `settle`.
- `settle(el, signal)` resolves when every animation in the subtree of `el` has finished or been cancelled (through
  `Animation.finished`, which covers animationend and animationcancel), at once when `el.getAnimations({ subtree:
  true })` is empty or reduced motion is on, and on abort. Call it right after the change that starts the
  animation. Games never listen for animationend themselves.
- Delays only between items entering in order, at most 0.3 s (design §7.1), longer only inside `[data-demo]`. No
  infinite animation. Thumbs never move (app.css stops animations under `[data-thumb]`).
- `reduced()` (reduced motion is on) is exported by lib/settle.js, the one copy (a code scan, 4.4): the balance's
  view.js and the story fixture import it, and the stories will (built 2026-10-30 for game 3: the two identical

### 2.8 Drawing, CSS and hooks

- A representation is a pure layout function (`layoutFrame(data)`, tested in Node for R6 [unit]) and a drawing
  function `drawFrame(host, data)` (condition 6), coloured only through role tokens (the second of two known parts in

- game.css: every selector starts with `[data-game="<id>"]`; keyframe names start with the id; no CSS nesting.
- A helper a second game needs moves to lib/ as it is, in a step of its own (CLAUDE.md "Shared code"), keeping the scans of
  4.4, as lib/weights.js did (2026-10-30). A game branch does not edit lib/ (section 7).
- **Linear marks, the pattern for new games** (game 3 first; the ten-frame and the balance keep their own layouts).
  A picture of many small marks is laid out in one module that imports nothing (stories: scene.js), as boxes whose
  every coordinate, size, stroke and font is a length `[a, b]` = a·u + b px, u the size of one object. The drawing
  puts each mark in one absolutely positioned span with its box inline as `--xu --xp --yu --yp --wu --wp --hu --hp`,
  and game.css has one positioning rule (`left: calc(var(--xu) * var(--u) + var(--xp) * 1px)`, and the same for top,
  width and height). The unit is solved in CSS from the stage, the ten-frame's pattern: `--u: min(var(--umax) * 1px,
  calc((100cqw - var(--dwp) * 1px) / var(--dwu)), calc((100cqh - var(--dhp) * 1px) / var(--dhu)))`, with `--dhu` and

  them, and every mark slides (no `transform: scale`). A move's offset (an arrival's start, a leaver's end) is
  a length and a share of the stage, `{ x, y, stage: [sx, sy] }` (CSS `sx * 100cqw`; the stage is the marks' nearest
  size container, and the drawing is centred in it): the drawing fills the stage only on the axis that limits u, so
  an offset from the drawing alone could start or end inside the panel; half the stage, half the drawing and 16px,
  the panel's largest padding, put it past the panel's clip on every screen. No geometry property in that game.css
  holds a literal length but a `1px` that multiplies a variable, and the digits' top padding that centres their ink
  (a code scan, 4.4). So a Node test solves every clearance at every u, and the
  browser draws the same numbers; a constant that fails changes in the layout module, never in CSS.
- **The balance's rows** (its own layout): `--cube` and `--cell` are registered `<length>`s, so the scene computes
  them once from the stage and `--rows` and every element under it inherits a number; `--rows` and `--len` take a
  display's size at once, with no transition. Moved frame by frame, every element solved the cube's `min()` of
  container units again and the whole scene was laid out on each frame: 9-16 frames over 34ms per display at 4x CPU
  on a Pixel 7, 0-2 now (hunt 2 #10; tests/balance.test.js scans game.css for both). Unlike the stories' `--dhu`,
  nothing there slides.

### 2.9 Skeleton

```js
import { settle } from '../../lib/settle.js';
import { drawFrame, drawDisplay, drawHint, drawTourDigit } from './frame.js';   // the game's own module

export const meta = { id: 'parts', title: 'חֲלָקִים', version: 1, css: new URL('game.css', import.meta.url).href };
export const levels = [{ id: 'split-5', skill: 'num.parts.split', demo: true, structure: 'part-whole', unknown: 'part',
  max: 5, model: 'frame', look: 'dots', options: 3, terms: false }];
export const text = [];
const count = (round, role) => round.picture.find((g) => g.role === role).count;
export const rules = { 'given.whole': (r) => count(r, 'whole'), 'given.part': (r) => count(r, 'part') };
export const displays = ['flash'];   // both rules' display (RULES); drawDisplay throws on any other

export function makeRound(level, rng) {
  let whole, part;
  do { whole = rng.int(3, level.max); part = rng.int(1, whole - 1); } while (part * 2 === whole);
  const answer = whole - part;
  const round = { skill: level.skill, structure: level.structure, unknown: level.unknown, look: level.look,
    model: level.model, eqform: 'standard', text: '', terms: [], helpPicture: null, answer,
    picture: [{ role: 'whole', count: whole, shown: 'tag' }, { role: 'part', count: part, shown: 'items' },
      { role: 'unknown', count: answer, shown: 'covered' }],
    equation: { left: [part, '+', '?'], right: [whole] } };
  round.choices = [{ value: answer, rule: null }, { value: whole, rule: 'given.whole' },
    { value: part, rule: 'given.part' }].sort((a, b) => a.value - b.value);
  return round;
}

export function render(host, round, { signal }) {
  const frame = drawFrame(host, round);   // cells, dots with data-role, a cover over the unknown
  return {
    async miss({ value, display, step }) {
      host.querySelector('[data-display]')?.remove();
      await settle(drawDisplay(frame, display, value, round), signal);
      if (step >= 2 && !frame.querySelector('[data-hint]')) frame.append(drawHint(round));   // not awaited (2.5)
      for (let n = 1; step === 3 && n <= round.answer && !signal.aborted; n++) {
        await settle(drawTourDigit(frame, round, n), signal);
      }
    },
    async solve() {
      const lid = frame.querySelector('.cover');
      lid.classList.add('is-lifted');
      await settle(lid, signal);
    },
  };
}
```

### 3.2 Screens and test hooks

- `main[data-screen]` is `home`, `round`, `demo`, `end`, `parents`, `dev`, `export` or `error`, with a `<title>`

- Bar: `[data-home]`, `role="progressbar"` (rounds done of 8), `[data-how]`. Panel `[data-area="picture"]`; equation

  `[data-show-picture]`. Control buttons have `data-control` and an `svg[data-icon]`.
- Every screen opens at the top: `screen()` scrolls the page to (0, 0) when it is scrolled. On a landscape phone a
  round is taller than the window, and it opened where the last screen was (the home page scrolled to a card, or the
  place of "הַבָּא"), so a story's event and its `?` played above the fold (playtest 2026-10-31).
- Cards' focus ring: the shell focuses the first card, and after a miss the next live one, so a keyboard works; app.css
  draws a card's `:focus-visible` ring only under `:root[data-keys]`, which a capture `keydown` listener sets and a
  capture `pointerdown` listener removes (start()). A page loaded straight at a round (iOS Safari reloads a discarded
  tab so) showed the ring, which a silent child reads as "this one", and after a miss it often landed on the answer
  (the cards ascend, the small error values first; playtest 2026-10-31). The same rule covers "הַבָּא" (`.next`), which
  the solve focuses: on iPhone a link tapped on home leaves Safari's focus state so that it showed the ring (bug hunt
  #7). "תַּרְאוּ לִי אֶת הַתְּמוּנָה" pressed with a key hands its focus on before it goes: to "הַבָּא" after the solve, else
  the first live card, so focus never falls to the page (bug hunt #23).
- A press and hold is a tap on the child's screens (app.css on `main:not([data-adult])`; `screen()` sets
  `data-adult` on the adults' screens, app.js's one list `ADULT`: the parents page, #/dev and the export):
  `-webkit-touch-callout: none` and `-webkit-user-select: none` (Safari 16.4 reads only the prefixed form), so iOS
  shows no link menu or preview on a home card and selects no text in the equation or a card (bug hunt #17).
  Android Chrome's link menu comes with the `contextmenu` event, which CSS cannot stop: `screen()` cancels it on
  every child's screen (`noMenu`), all but the round's JSON on #/dev; the adults' screens keep it. A new adults'
  screen goes in `ADULT` alone (tests/code.test.js: no stylesheet names a screen there). A
  locked card (`[data-choices][data-locked]`: a display, a demo, the solve) does not sink under a press; one held
  until the lock ends sinks then and is taken on release (bug hunt #18).
- main's one column is `minmax(0, 1fr)`, and the equation area and row have `min-width: 0`: a row wider than its box
  overflows it, so `fitEquation` shrinks it to 28px and then wraps it, and nothing widens the column past main's
  content box (it took both gutters at 320px on balance level 8's `10 + 10 = ? + 18`, bug hunt #9; site.spec.js
  checks each level's widest exercise at 320, 4.6). `fitEquation`
  runs again on every resize of the round's screen, so a turned phone shrinks the row on the narrow screen and gives
  it its full size back on the wide one: fitted once, that row (48px at 568×320) spilled 8px into each gutter when
  turned to 320×568, and one shrunk at 320 stayed 31.2px sideways (the class of bug hunt #11, 2026-10-31).
- Off-target taps: a press of the primary pointer that hits no button and no `[data-target]` is counted by the
  nearest `[data-area]` (`picture`, `equation`, else `other`) until the solve, once it ends as a tap: its pointerup,
  with no pointercancel and no second finger between. A scroll (the browser takes the touch and cancels it) and a
  pinch are no taps (2026-11-01: counted on pointerdown, one swipe was one tap, a pinch two, and on a phone held
  sideways every round needs a scroll to reach its cards; hunt 2 #6). A press the double-tap window drops is not
  counted: its pointerdown never reaches the screen.
- Double tap (design 6.9; owner decision 2026-10-14, "חלון של 0.3 שנייה"): the shell drops a tap that comes within
  300 ms of a change under the finger: a screen drawn (`screen()`: every route, round and demo) or "הַבָּא" put in
  the cards' place, where it stays until the next screen. shell/taps.js decides on event times alone. A change is
  stamped with `new Event('change').timeStamp`, the clock input events are stamped with; capture-phase `pointerdown`
  and `click` listeners on the root drop (`preventDefault`, `stopImmediatePropagation`) an event stamped less than
  300 ms after the change, or before it (a tap queued while the screen changed). A click goes with its pointerdown,
  so a press that came down in the window stays dropped however long it lasts; a keyboard click goes by its own time.
  A click is a pointer's when it has a `pointerType` (Chrome's click is a PointerEvent, with `''` from the keyboard),
  else when its `detail` is above 0 (Safari 16.4's click is a MouseEvent): Chromium gives a touch click `detail` 0
  when the shell dropped its pointerdown and the last click was a mouse's. No `setTimeout` or `setInterval`; nothing
  locks or waits, and a tap after the window is taken. So
  the second tap of a double tap never answers a round the child has not seen, never skips the solved picture (also
  with reduced motion), and never opens a game from the end screen's home button, in every browser: the window
  counts no taps in `detail`, which iOS Safari never sets above 1. It replaced a `detail` guard that worked in
  Chromium only.

### 3.3 Session

- 8 counted rounds (demos do not count), as a list of `{ game, level, seed, kind, structure?, ask? }`: 0 to 2 review
  rounds (3.5), then new rounds in the chosen game. The 8 seeds come from the session seed through `rng`. A new
  round's level is filled in when it starts, so the ladder moves within a session.
- No exercise twice in a session: when a round starts (before its demo), its seed goes up by 1 while its round is
  an exercise the session dealt already, 50 tries at most (`apart` in app.js, `apartSeed` in shell/planner.js). The
  same exercise is `exerciseOf(game, round)` in shell/planner.js: the game, the answer and the two sides of the
  exercise in either order, so a reversed row or another verb is the same and `3 + 2` is not `2 + 3`; a round with no
  exercise by its picture. The seed recorded, and the screen's `data-seed`, are the ones played. On a level of 9 or
  10 exercises (the stories to 5) the same exercise, with its answer on the same card, came back in 98% of sessions
  (playtest 2026-10-31); makeRound stays pure.
- A demo's exercise counts as dealt (2026-11-01): the entry demo and "show me how" solve an exercise the session has
  not dealt (3.8), and the rounds after it come apart from it, so the hand's answer does not come back to be copied
  while the level has an exercise the session has not dealt. On `whole-5` (7 exercises) it does: the entry demo's,
  dealt second, is the second to come back, as round 8 (below). Before, a demo's exercise came back as a later round,
  logged `first`, in rounds 2-4 of 15-50% of a demo level's sessions (stories level 6 about 49%, ten-frame 1 and
  stories 1 about 37%, balance 1 about 15%; hunt 2 #2).
- When every try is an exercise the session dealt, the try dealt longest ago comes back (the session maps each
  exercise to when it was dealt; 2026-11-01), never the last one while another can. Level 1 of the stories
  (`add-5`) and the ten-frame's level 1 (`split-5`) have 9 exercises, so a demo and 8 rounds are apart,
  except when the 50 tries all miss the one exercise left: then the oldest, round 1's, comes back as round 8 (about
  0.3% of the sessions that stay at `add-5`, 1.6% at `split-5`, whose exercises are not equally likely;
  4000 sessions each, 2026-11-01). Level 4 (`take-5`) has 8 since `4 − 2` left (section 6, "Doubles in stories"), so
  a session that stays there deals round 1's exercise again as round 8 (3991 of 4000 sessions); the demo's does not
  come back. Level 6 (`whole-5`, the basket to 5 without 0 and equal parts) has 7, so a session
  there deals two again, the oldest first: round 1's as round 7, the demo's as round 8. Before, the 51st try was
  kept, a random one of the 7: the previous round's exercise in 14% of sessions (hunt 2 #11). A level of fewer than
  8 exercises is named in tests/games.test.js (`SMALL`, 4.2).
- Mixed level: a second `rng` from the session seed picks each round's structure (or `ask`): the first uniformly,
  then another value with probability 0.4 (R3, R11). Kind `mixed`.
- After a stuck return (3.7) the remaining new rounds go to the target, and the next step holds there (3.6); in
  another game the address names it (3.7).
  Leaving mid-round drops that round.
- End screen: solved thumbs of the rounds played, and the home button (R10, §5.10).

### 3.4 The ladder, per game

State `{ level, fast, streak, window, passed, at, demoSeen, demoDue, hold }`; `level`, `passed` and `demoSeen` hold
level ids; `fast` is the id of the level the climb started at, or null; `at[id]` is `{ n, first, sessions,
lastSession }`; `demoDue` and `hold` are the level of a stuck return (3.7), or null. A new state starts at level 1
(or the next-step target) with `fast` set.

- Review rounds change nothing. Mixed rounds count toward going up, not in the down window.
- **Fast climb:** a first try marks the level passed, adds it to `demoSeen` (the child showed it), and goes up one
  (the last level stays). Any other outcome sets `fast` to null: at a level reached by a fast promotion and not yet
  passed, go back one level and unmark it (one success may be a guess); at the start level, at the last level once
  passed there (it is the last level passed on a first try), after a mixed round (§5.6), and at a level with
  `down: false` (below), stay.
- **Normal:** `first` adds 1 to `streak`, anything else resets it. `window` keeps the last 4 outcomes at this level
  and is emptied on every level change. Streak 4: mark passed, go up (the last level stays). Two outcomes in the
  window that are not `first` (`shown` included): go down one (level 1 stays, window emptied), except from a level
  with `down: false` (a skills.md parameter), which stays with its window emptied, as level 1 does.
- **`down: false`** marks the first level of a skill whose level below in the list is another skill's, one this skill
  does not build on: going there eases nothing. The stories' levels 1, 4 and 6 have it (three skills one after
  another: a child stuck on take to 5 was sent to `4 + ? = 10`, and one stuck on the basket to 5 to take to 10 in
  reversed forms). At such a level the fast climb's miss stays too, and the level below stays passed (a miss on take
  to 5 unmarked add-change), and the stuck rule (3.7) does not fall back to the level below either. Since 2026-10-31
  also ten-frame level 8 and balance levels 10 and 11, the three boundaries of the ten-frame and the balance whose
  level below is no prerequisite (section 6). The generic test (4.2) fails a level whose level below is another
  skill, not among its `prereqs` (base and each `when` it meets), unless it says `down: false`; balance level 9 steps
  down, since its `when` (`unknown: both-sides`) needs both-sides. Playtest 2026-10-31.
- **Stuck:** `at[id]` counts rounds, first tries and distinct sessions at a level across visits until it is passed.
  At `n >= 10`, `sessions >= 2` and `first / n < 0.5` the counters reset and the planner picks a target (3.7).
  Passing the `hold` level sets `hold` to null.
- **Demo** (R9): a new round runs the demo first when its level has `demo: true`, is not in `demoSeen`, and was not
  just reached by a fast promotion. So the start level's demo runs (nothing is known yet), and after a fast climb
  ends, the demo of the level where it ended runs when the child gets there again. The entry demo adds its level
  to `demoSeen` (and clears a `demoDue` of that level) once the hand has tapped the answer, not when it starts: a
  reload, home or a closed tab in the middle of it brings it back on the next entry, as R9's watching round. Before
  2026-10-31 it was added at the start, and a demo left half-way was lost for good; the hand button costs the child
  the round's first try. Only the entry demo marks it; "show me how" does not.

### 3.5 Passed, review, mastered

- A skill is passed when its last level, in some game, is passed (used by the next step).
- **Schedule** (R11): from the day a level of the skill is first passed, `box` 0 and due the next day. After a review,
  a first try moves `box` up one (to 3 at most), anything else sets it to 0; due is that day plus 1, 3, 7 or 14 by
  `box`.
- **Pool:** every scheduled skill with a passed level in any registered game, last played before today, ordered by
  due date, then SKILLS order. No grade band (owner decision 2026-10-14; it replaced pedagogy §8.1 ד's band of
  grades 1-2). Two review rounds when two or more are due, else one: the first in order, due or not. Nothing
  scheduled: no review.
- **Level:** the highest passed level of the skill (ties: first game in home order); after a failed last review of
  the skill, one lower if that level has the same skill, model and look. No demo; a mixed level gets a picked
  structure, kind stays `review`.
- **Mastered** (R11, used by the stuck rule): passed, and first-try reviews on 2 different days after that. Never
  shown.

### 3.6 Next step (§5.12)

- **Order:** the learning order, SKILLS as data/skills.js lists it. It comes from the prerequisite graph, never from
  a grade (owner decision 2026-10-14): `learningOrder()` in scripts/gen-data.js sorts the skills.md rows by
  prerequisite depth (the longest chain of `base` prerequisites below a skill; a skill with none has depth 0), then
  by row order. Every base prerequisite is shallower than its skill, so this is a topological order: a skill never
  comes before its base prerequisites. Conditional prerequisites (`when`) gate the level that meets them (below),
  not the order: counted in the order, `eq.props.commutative`'s `[op=mul] muldiv.meaning.array` would put
  `addsub.facts.count-on` after multiplication. The generator writes the order; the code never sorts. The grade
  column of skills.md is school information only, and no code reads it. An explicit sequence column (the
  Aharoni/Singapore order) can later replace the row-order tie-break with a change to the generator only.
- **Prerequisites** for a level: `base`, plus each entry of `when` whose condition the level meets. Conditions keep
  the skills.md bracket: `{ max: '>20' }` compares numbers, `{ op: '=mul' }` tests equality (membership for arrays).
  So a level whose conditional prerequisite is offered and not passed waits, though its skill comes early.
- A skill no registered game offers is skipped, and counts as met when it is a prerequisite.
- **Held:** while a game's ladder has a `hold` (3.7), the step is that game at its ladder level (no jump), first in
  home order if two hold.
- **The step:** the first skill in order that a game offers, not passed, with its prerequisites (for the level it
  would open) passed or offered by no game. Game: the first in home order that offers it. Level: the game's level if
  it has that skill, else the lowest unpassed level of the skill there; following the step moves the game there
  (event `jump`). A new game state starts its fast climb there. Nothing left: the first game at its level.

### 3.7 Stuck child (§5.4)

Walk the stuck skill's prerequisites in written order (base, then met conditions). The first that is not mastered
and is offered by a game wins: that game, at its highest passed level of that skill, else the skill's first level
there. Unmastered prerequisites no game offers go into `missing`. If none wins: the previous level of the same skill
in this game, else the previous level in the list, else stay. A level with `down: false` (3.4) skips the previous
level in the list, which is another skill's and no easier, and stays (2026-10-31): the target is the stuck level, its
demo runs once more and it is held, as at a game's first level. The target game moves to the target level
(`moveTo(..., again)`), whose demo runs once more (`demoDue`), and the event `stuck` `{ game, level, skill, to: { game,
level, skill }, missing }` is written. The target is held (`hold`): the rest of the session plays there, and the next
step points there until the child passes the target level, so a stuck return on a session's last round still leads
to the prerequisite and its demo. When the target is in another game, the stuck game keeps its own level, and the
address becomes `#/play/<target game>` (`history.replaceState`, no hashchange), so a reload or a tab Safari restores
opens a session there (2026-11-01; it named the stuck game, whose new session opened at the stuck level with its
stuck counter reset; hunt 2 #12). Only while the address still names the session's game: home tapped during the
closing has left it, and `route()` applies the solved round (`sync`) before it reads the address, so without that

### 3.8 Random

`rng(seed)` is mulberry32 over a uint32: `{ next(), int(lo, hi), pick(list), shuffle(list) }` (a number in [0, 1),
an integer with both ends included, an element, a new array). makeRound uses nothing else.

The demo's seed (R9: the watching round, then a round "with other numbers"; 2.6) is `demoSeedFor(make, seed,
dealt)` in shell/planner.js, pure and tested: from `demoSeed(seed)`, `(seed ^ 0x9e3779b9) >>> 0`, it goes up by 1 to
the first round that has other numbers than the round it shows how to solve, is plain, and is no exercise the session
dealt (`dealt(round)`, when it was dealt, 3.3; #/dev has no session), `TRIES` (50) at most.

- Other numbers: another answer (`same`, deep and key-order free, so never the same exercise in any form or
  drawing), and, where both rounds have an exercise row, another row, its two sides in either order: `? + ? = 5`
  dealt twice is one exercise with two answers (ten-frame level 4, 11.9% of its demos before).
- Plain (`plainDemo`): no number of the answer is 0 or a number the row shows. A worked example is then not an
  edge round (`10 + ? = 10`, `a + ? = a`, a pair with 0) and not a double whose answer is the given part
  (`2 + ? = 4` reads as given.part's card). A judging card is no number; a round without a row checks only 0.
- None within 50: of the rounds with other numbers, the first not dealt; else a plain one dealt, then any, the one
  dealt longest ago (a level of 7 exercises late in a session); else the first demo seed. Only the balance's `turn`
  (level 9, no demo of its own; "show me how" reaches it) finds no plain round: its answer is always a number of its
  row (`5 + 4 = 4 + ?`).
- The demo's exercise then counts as dealt (3.3), so a second "show me how" on the same round shows another one.

Before 2026-10-31 the seed went up only while its round was the real one's exercise (`exerciseOf`, 3.3; first
deep-equal): the hand tapped the round's own answer in up to a third of a demo level's demos (the stories' level 6
33.4%, ten-frame 1 22.4%, balance 1 12.5%: `3 + 5` and the 8-pile, then a round whose answer is 8), solved an edge
round in up to 30% (ten-frame 4 29.9%, a pair with 0; ten-frame 5 26.9%, `10 + ? = 10` or `5 + ? = 10`), and a
copied tap was logged `first` and fed the fast climb. tests/games.test.js checks every game, fixtures included, at
every level and mixed value over seeds 1-2000 (`checkDemo`, 4.2).

### 3.9 Storage (§5.11, dev-spec A.4)

- One localStorage key, `sifra`: `{ schema: 1, current, children: { [childId]: Child } }`. Child: `{ created,
  sessions, games: { [gameId]: ladder state }, skills: { [skillId]: { last, passedDay, box, due, reviewDays,
  lastReviewFirst } }, attempts, events }`. The child id is `c` plus 8 hex digits from crypto.
- Storage is read only inside start and route handlers (the export reads when opened), always in try/catch; when it
  throws or is missing, the shell plays from memory. `migrate(raw, newId, { t, day })` (the load's time and local
  day): a schema newer than the code, whatever its shape, is checked first: play from memory, never write; then
  missing, unparsable or broken (no current child object) gives a new value, and when something was stored, the new
  child's `repair` event keeps it whole under `*` (the first save overwrites it, other children included); schema 1
  stays; each new schema adds a step. Then every stored child is brought to `SHAPE` (store.js, pinned to the schema
  by tests/store.test.js, so changing a key of a child, a ladder or a skill state needs a schema step): a missing or
  wrong-typed value takes its default (a ladder's `fast` null), a ladder whose `level` is not a string and a skill
  state that is not an object are dropped, keys outside the shape stay, and whatever was replaced or dropped is kept
  in one `{ t, day, type: 'repair', lost }` event, `lost` mapping each path (`sessions`, `games/scale`,
  `games/parts/passed`) to the value it held, so no progress goes silently and the export still holds it; should a
  record still make the planner throw, home opens without the next-step card and `#/next` goes home, and a thumb
  that throws is left empty and marked `data-broken` (the error goes to the console), so the error screen's way
  home always opens. The catch sees only a synchronous throw, so `render` draws a thumb before it returns (2.4): a
  rejection from a chain a thumb started would reach the error screen, and its home button would land on the same
  thumb again.
- Written after each solved round, each session's start (the session count), an entry demo's start only when it
  starts a game's first ladder, its tap on the answer (`demoSeen`, 3.4), and each jump. Before 2026-11-01 every entry
  demo wrote the whole store again at its start, the same text the session's start had just written (two writes of
  60-100 ms each on a large store on a slow phone; hunt 2 #15). Caps: 4000 attempts and 500 events, oldest first out; on a
  quota error the oldest half of the attempts is set aside and it retries once; if the retry fails too, nothing was
  written, so the half comes back and nothing is lost from memory (bug hunt #21). `navigator.storage.persist()` runs
  once per start.
- Storage is read again before each write (`refresh` in store.js, bug hunt #8): at each route, at the top of each
  round, as the entry demo is seen, and for a solved round once its closing has run, at the write itself (`persist`
  applies `S.pending`, the round's ladder step, review, stuck return and attempt, on what it has just read; so does
  the `pagehide` and hidden flush): two visible tabs (iPad split view, a desktop) may write within one closing, and a
  write applied before the closing undid the other's. Another tab of the site (a WhatsApp link
  opens a new Safari tab, and old tabs keep their state for days) may have written since this one read or wrote;
  `save` writes the whole store, so without it one tab undid the other's progress. A stored text other than the
  last one this tab read or wrote (`raw`) replaces memory, migrated, when this code can read it; a newer schema keeps
  memory and makes the tab not writable (2026-11-01, hunt 2 S-c: before, an empty child replaced it); a failed read,
  nothing stored or a broken value keeps memory. A solved round steps its game's ladder only when the ladder still
  stands at the round's level (another tab may have moved it); the attempt and the review schedule are written either
  way. So a ladder at a level id this code lacks (an old tab, after a newer one moved it to a level added since)
  plays level 1 and never steps, keeping the newer tab's progress, until the next step's jump moves it (`moveTo`,
  3.6; e2e/fixtures.spec.js, hunt 2 S-b). The `storage` event alone would not do: a frozen iOS tab may never get it.
- An attempt (CLAUDE.md "ready to grow" 3, §5.11): `t`, `day`, `session`, `child`, `game`, `level`, `levelId`,
  `skill`, `seed`, `version`, `params` (the level as passed), `answer`, `kind`, `outcome` (`shown` if the tour ran;
  `help` after any miss, `picture` or `how`; else `first`), `wrong` (rules in tap order), `firstMs` and `ms` (from
  the mount to the first tap and to the correct tap; one read of the clock when the first tap is correct, so equal),
  `help` (`hint`, `tour`, `picture`, `how` in arrival order), `demo` (the demos shown before the correct tap, in
  order: `auto` on entry, `how` for the hand; `[]` for none), `taps` (off-target, by area), `options`,
  `levelBefore`, `levelAfter` (the game's level once the round is applied, a stuck return that moved this game
  included), `sinceDays`.
  The round itself is not stored: seed, `version`, `params` and `answer` rebuild it. The attempt is taken once, at
  the solve (its `t` and `day` too), from copies of the round's record, and never changes after it: an off-target
  tap or the picture button after the solve is not logged.
- Export: a button (iOS downloads need a tap) that saves `sifra-<child>-<day>.json`, `<day>` the local day like every
  day in the store: `{ key: 'sifra', schema, exported, persisted, data }`, `exported` the ISO time and `data` the
  stored value as is.

## 5. npm, tsconfig and CI

```json
"scripts": { "test": "node --test", "typecheck": "tsc -p tsconfig.json", "e2e": "playwright test",
  "check": "npm test && npm run typecheck && npm run e2e", "gen": "node scripts/gen-data.js",
  "lock": "node scripts/lock-rounds.js", "start": "node start.js" },
"devDependencies": { "@playwright/test": "1.56.1", "typescript": "5.9.3" }

{ "compilerOptions": { "target": "es2022", "module": "es2022", "moduleResolution": "bundler",
    "lib": ["es2022", "dom", "dom.iterable"], "allowJs": true, "checkJs": true, "noEmit": true,
    "strict": false, "noImplicitAny": false, "noUnusedLocals": true, "skipLibCheck": true },
  "include": ["types.d.ts", "app.js", "shell", "lib", "games", "data"] }
```

- `node --test` finds `tests/**/*.test.js` and not the e2e specs. `check` is the full gate.
- `npm run lock` rewrites tests/rounds.lock.json (4.1) after a game's version (`meta`, 2.1) goes up, or a game or
  level is added; it writes nothing while a level's rounds changed without a bump or a locked game or level id is
  gone.
- `noUnusedLocals`: an import, variable or function nothing reads fails the typecheck (an import a merge brought
  back, 548c6dd). Unused parameters stay allowed: a game's `render` and `face` keep the contract's signature.
- The ES2022 lib keeps some APIs newer than Safari 16.4 out (`Object.groupBy`, `Promise.withResolvers`), but its DOM
  part has newer ones, and CI's WebKit is Playwright's current WebKit, not Safari 16.4; neither enforces the target.
  A code scan does (4.4). Only the browser code is type-checked: tests, scripts and e2e would need `@types/node`, and
  the dev dependencies stay two.
- CI (.github/workflows/ci.yml), on a push to any branch (`branches: ['**']`, so not on a tag), pull requests and
  workflow_dispatch: job `check` (Node 22: `npm ci`, `npx playwright install --with-deps chromium webkit`,
  `npm run check`); job `deploy` (a push to main only, after `check`): the deployed files (section 1) to `_site` with
  `.nojekyll`, `actions/upload-pages-artifact@v3`, `actions/deploy-pages@v4`. A branch push runs the full check and
  deploys nothing, so WebKit runs before the merge: agents often have Chromium only, and three WebKit-only failures
  (114e1b6, 4f84173, 0b1cf85) were first seen on main, where they blocked the deploy. A branch with an open pull
  request is checked twice, once per event. Nothing makes a merge wait for the branch's run: merges are made
  locally, without a pull request, and requiring the check is a GitHub setting only the owner can make. So it is a
  working rule GitHub does not enforce: a branch is merged to main only after its run passes (section 7, "Done").
- The Pages source must be "GitHub Actions" (Settings > Pages > Build and deployment > Source; only the owner can set
  it). With "Deploy from a branch", GitHub's own `pages-build-deployment` also publishes the raw branch through
  Jekyll on every push to main, within a minute and whatever the check's result. After a push to main, the Actions
  list shows only the CI run for that commit, and the `github-pages` deployment comes from its `deploy` job.
